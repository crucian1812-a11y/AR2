# BJJ Game — план разработки

Мобильная игра про бразильское джиу-джитсу на Unity. Целевой артефакт — `.apk`
для Android, собираемый в GitHub Actions.

---

## 1. Что делаем: концепция

Не «мордобой с полосками здоровья», а **позиционная борьба**. Это принципиально:
именно из этого растёт и глубина геймплея, и уникальность на фоне UFC-игр.

**Матч** — раунд(ы) по 5 минут. Победа:
- **сабмишн** — мгновенная победа (главная цель),
- **по очкам** (правила IBJJF), если время вышло:
  - тейкдаун — 2, свип — 2, колено на животе — 2,
  - проход гарда — 3, маунт — 4, спина с крюками — 4.

Очки — это и счёт, и обучающий сигнал: игрок физически чувствует, что
продвижение по позициям = прогресс.

### 1.1. Ядро — граф позиций

Вся игра — это конечный автомат позиций и переходов между ними.

```
Стойка (борьба за захваты)
  ├─ тейкдаун (дабл-лег, сингл-лег, сеой-наге, оучи-гари) → Топ
  └─ pull guard                                          → Закрытый гард

Снизу: закрытый гард · открытый · полугард · баттерфляй · Де Ла Рива · черепаха
Сверху: сайд-контроль · маунт · спина · колено на животе · норт-саут · полугард топ

Сабмишны: RNC, треугольник, армбар, кимура, гильотина, американа, омоплата,
          хил-хук, эзекиль, крестовое удушение из маунта
```

Каждый переход — ребро графа со своими условиями: нужный захват, окно по времени,
запас стамины, «база» (распределение веса) соперника. Модель данных —
ScriptableObject на каждую позицию и каждый переход, чтобы контент правился без
кода и без пересборки.

### 1.2. Три ресурса вместо здоровья

| Ресурс | Что делает |
|---|---|
| **Стамина** | Тратится на захваты, взрывные переходы, защиту. Восстанавливается в доминирующей позиции и на отдыхе. Пустая стамина = защита почти не работает. |
| **Захваты (grips)** | Кто держит рукав/отворот/шею. Определяет, какие переходы вообще доступны. |
| **Опасность сабмишна** | Растёт, пока приём затягивается; при 100% — тап. |

Полоски здоровья нет вообще. Проигрыш — это тап или счёт.

## 2. Управление (как в UFC, но под палец)

Ландшафтная ориентация, две зоны большого пальца.

**Левый палец — база и давление.** Виртуальный стик: наклон = перенос веса,
постура, поднятие/опускание бёдер. Держишь давление сверху — соперник не может
восстановить гард, но твоя стамина утекает.

**Правый палец — зона жестов, аналог правого стика в UFC.**
- свайп ↑ — пройти гард / поднять постуру
- свайп ← / → — свип, роллинг, смена стороны
- свайп ↓ — вернуть гард, подтянуть соперника
- долгий тап — вход в сабмишн из текущей позиции
- двойной тап — взрывной рывок (много стамины, короткое окно)

**Каждый переход — короткая борьба, а не кат-сцена.** Появляется «grapple bar»:
атакующий тянет её в свою сторону удержанием направления, защищающийся должен
свайпнуть в противоположную сторону в окне ~0.4–0.7 с (окно шире, если больше
стамины). Это ровно та механика «grapple assist» из UFC 4, только на свайпах.

**Сабмишны — две разные мини-игры для двух сторон:**
- *Атакующий*: сжимающееся кольцо, тап в зелёном секторе затягивает приём;
  промах — теряешь позицию контроля.
- *Защищающийся*: тянешь узел-маркер из «красной зоны» пальцем, стамина утекает;
  можно выбрать «терпеть и выходить» (медленно, дешевле) или «взрывной выход»
  (быстро, дорого, риск отдать спину).

**Тактильная отдача (haptics)** на каждую смену захвата, фиксацию позиции и
затягивание приёма. Дешёво в реализации, а ощущение веса даёт огромное.

**Ассист-режим** для новичков: подсказки-стрелки доступных переходов, как в
UFC 4. Отключается в «Pro».

## 3. Графика: как выжать AAA-вид из телефона

Честно: «AAA» на мобиле — это не про рендер-фичи, а про **качество моделей,
анимации и подачи камеры**. Именно туда идёт основной бюджет внимания.

**Рендер-стек:** Unity 6 LTS + **URP** (Forward+). HDRP на Android не
поддерживается — этот вариант отпадает сразу. Vulkan, IL2CPP, ARM64, ASTC-сжатие
текстур.

**Что реально создаёт «дорогую» картинку:**

1. **Кожа.** Главный маркер реализма. Кастомный шейдер: wrap-lighting +
   curvature-карта + лёгкое подповерхностное рассеивание (аппроксимация, не
   полноценный SSS). Без этого бойцы выглядят как пластик.
2. **Пот и блеск, нарастающие по ходу раунда.** Динамическая карта roughness +
   wetness-оверлей, который усиливается со временем матча. Очень дёшево по
   производительности и мгновенно читается как «дорого».
3. **Ги (кимоно).** Не Unity Cloth — он тяжёлый. Либо запечённая анимация ткани
   в клипах, либо лёгкая симуляция на 6–10 костях (Magica Cloth / Dynamic Bone).
   Плюс отдельная карта микро-ворса на ткани.
4. **Свет.** Запечённые лайтмапы арены + один реалтайм key-light с мягкой тенью
   на бойцах + reflection probe. Спортзал/арена — идеальная сцена: замкнутая,
   можно вылизать.
5. **Пост-обработка:** HDR, ACES-тонмаппинг, bloom, SSAO, лёгкое зерно,
   виньетка, хроматика в момент фиксации приёма, DOF в сабмишн-камере.
6. **Камера — половина эффекта.** Cinemachine 3, свой ракурс под каждую позицию
   (телевизионная подача), медленное сближение при затягивании приёма,
   slow-motion на финише, автоповтор концовки с другого ракурса.
7. **Толпа и звук.** Импостеры-биллборды по периметру + реактивный эмбиенс:
   зал затихает на входе в сабмишн и взрывается на тапе. Звук здесь работает
   сильнее, чем ещё +10k полигонов.

**Бюджеты (тир «High», Adreno 730 / Mali-G78 и выше):**

| | Бюджет |
|---|---|
| Полигоны на двух бойцов | 80–120k tris суммарно |
| Текстуры бойца | 2K, ORM-упаковка (3 канала в 1 текстуру) |
| Реалтайм-тени | 1 источник, каскад 1–2 |
| Draw calls | < 120 (SRP Batcher + GPU Resident Drawer) |
| Целевой FPS | 60 на High, 30 на Low |

Три тира качества (Low / Medium / High) с автоопределением по железу — иначе
на бюджетных телефонах будет слайд-шоу.

## 4. Анимация — самое узкое место

**Это главный риск проекта, и решается он выбором ассетов, а не кодом.**

Борьба — это *парные* анимации: две модели в контакте, руки должны реально
держать, а не проходить сквозь. Варианты:

- **(A) Парные клипы** — обе фигуры анимированы вместе и экспортированы одним
  FBX с двумя скелетами (или двумя синхронными клипами с общей точкой отсчёта).
  При проигрывании корни жёстко привязываются друг к другу. **Это единственный
  путь, дающий приличный результат.**
- **(B) Одиночные клипы + IK-доводка.** Дешевле, но руки скользят и проваливаются
  в тело соперника. Для борьбы вплотную выглядит плохо.
- **(C) Захват движения / покупка mocap-библиотеки.** Дорого.

**Следствие: список приёмов в игре определяется тем, какие парные клипы есть в
ассет-паке.** Поэтому граф позиций проектируется *после* того, как я увижу
содержимое пака. Mixamo, к слову, для партера почти бесполезен — там нет
парных грэпплинг-клипов.

Технически: Animancer или Playables API для плавных переходов, Animation Rigging
для доводки хвата рук по цели.

## 5. Сборка APK через GitHub Actions

Локально Unity здесь нет, поэтому сборка — только в CI:

- **GameCI** (`game-ci/unity-builder@v4`), target `Android`, `ubuntu-latest`.
- Секреты Unity: `UNITY_EMAIL`, `UNITY_PASSWORD` + `UNITY_LICENSE` (Personal)
  или `UNITY_SERIAL` (Pro/Plus).
- Подпись APK: `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASS`,
  `ANDROID_KEYALIAS_NAME`, `ANDROID_KEYALIAS_PASS`.
- Результат — артефакт workflow: скачал `.apk`, поставил на телефон.
- Первая сборка идёт 20–40 минут (образ Unity ~10 ГБ), последующие — быстрее
  за счёт кэша `Library/`.

Отдельная заметка: значения секретов GitHub не читаются ни через API, ни мной —
это by design. Мне нужны только **имена** секретов, чтобы вписать их в workflow.

## 6. Этапы

| Этап | Содержание | Результат |
|---|---|---|
| **M0. Пайплайн** | Ветка, LFS, Unity-проект, CI | Пустой APK ставится на телефон. Проверяем сборку **до** любого контента. |
| **M1. Серый бокс** | Граф позиций, переходы, стамина, очки, 1 сабмишн — на капсулах | Играбельное ядро без графики |
| **M2. Бойцы** | Модели, парные анимации, риг, Cinemachine | Похоже на бой |
| **M3. Управление** | Жесты, grapple bar, мини-игры сабмишнов, haptics, ИИ соперника | Играется приятно |
| **M4. Графика** | Кожа, пот, ги, свет, пост, звук, толпа | Выглядит дорого |
| **M5. Мета** | Меню, выбор бойца, карьера/турнир, настройки, тиры качества | Готовая игра |

Порядок не случаен: **M0 первым**, потому что сломанный CI на этапе M4 — это
потерянная неделя. Графика — предпоследней, потому что полировать нужно то, что
уже играется.

## 7. Открытые вопросы

1. **Ссылка на ассеты** — без неё нельзя спроектировать граф приёмов (см. §4).
2. **Есть ли Unity Editor на твоей машине?** Если нет — я пишу проект целиком
   текстом (сцены/префабы — это YAML), и всё собирается в CI. Так можно, но
   тогда порядок работ другой.
3. **Имена секретов Unity** в настройках репозитория.
4. **Репозиторий публичный.** Платные ассеты с Asset Store в публичный репозиторий
   класть нельзя по лицензии — см. `ASSETS.md`.
5. **Ги или ноги (без кимоно)?** Ги — сложнее по ткани, но богаче по захватам.
   No-gi — проще визуально, но нужна хорошая кожа и татуировки.
